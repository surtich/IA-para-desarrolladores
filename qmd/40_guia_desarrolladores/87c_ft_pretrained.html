Ajuste fino en un modelo preentrenado

Introducción

Un modelo preentrenado (pretrained model) es un modelo de lenguaje que ha sido entrenado previamente en una gran cantidad de datos para aprender patrones y representaciones del lenguaje. Estos modelos únicamente son capaces de generar el siguiente token dada una secuencia de texto, pero no pueden realizar tareas específicas sin un proceso adicional de entrenamiento. El ajuste fino (fine-tuning) es el proceso de tomar un modelo preentrenado y entrenarlo adicionalmente en un conjunto de datos específico para que pueda realizar una tarea particular, como clasificación, generación de texto, traducción, entre otras.

PEFT y LoRA

Utilizaremos el ajuste fino eficiente en parámetros (Parameter-Efficient Fine-Tuning o PEFT) y la adaptación de bajo rango (Low-Rank Adaptation o LoRA) para ajustar nuestro LLM (Modelo de Lenguaje Grande). Pero antes de intentar definir estos términos, es necesario entender por qué existen estas modalidades de entrenamiento.

Ajuste Fino Tradicional frente a PEFT

Con el ajuste fino tradicional (o regular), como se mostró en el tema anterior, actualizamos todos los parámetros del modelo de lenguaje al entrenarlo con datos nuevos. Esto permite que el modelo aprenda nueva información y se adapte a las características específicas de los nuevos datos, mejorando su rendimiento general en la tarea objetivo. Esta técnica genera mejoras de rendimiento significativas, especialmente cuando se dispone de datos suficientes, y es relativamente sencilla de implementar.

Por otra parte, este enfoque es computacionalmente muy costoso y requiere mucho tiempo. También exige una cantidad de datos mucho mayor para evitar el sobreajuste (overfitting). En este problema común del aprendizaje automático, el modelo aprende los datos de entrenamiento con demasiada precisión, incluyendo el ruido y los detalles específicos que son únicos de ese conjunto de datos en particular. En lugar de capturar los patrones generales subyacentes, el modelo esencialmente memoriza los ejemplos de entrenamiento. Esto se traduce en un rendimiento excelente en los propios datos de entrenamiento, pero en un rendimiento significativamente inferior cuando se le pide al modelo que realice predicciones sobre datos nuevos y no vistos.

Sin embargo, lo más preocupante es que este tipo de entrenamiento provoca el olvido catastrófico (catastrophic forgetting). Si se vuelve a entrenar un modelo con un nuevo conjunto de datos sin aplicar ninguna técnica especial, el modelo podría sobrescribir por completo el conocimiento que había adquirido del primer conjunto de datos.

Aquí es donde entra en juego PEFT. Los métodos PEFT introducen una pequeña cantidad de parámetros adicionales al modelo en lugar de modificar toda la matriz de pesos original. Esto reduce drásticamente el número de parámetros entrenables, haciendo que el proceso de ajuste fino sea más eficiente y menos costoso a nivel computacional.

Al tener menos parámetros entrenables, el proceso de entrenamiento requiere menos memoria y recursos computacionales. Esto se traduce en tiempos de entrenamiento más rápidos, especialmente para modelos grandes.

LoRA (Low-Rank Adaptation)

LoRA es uno de los métodos de PEFT más populares. Se basa en una hipótesis clave del aprendizaje profundo: las actualizaciones de los pesos de una red neuronal durante el ajuste fino tienen una “dimensión intrínseca baja”.

Esto significa que, aunque una matriz de pesos original sea gigantesca, los cambios necesarios para que aprenda una nueva tarea se pueden proyectar en un espacio matemático mucho más pequeño sin perder apenas información.

A continuación, desglosamos la ecuación y el álgebra lineal que hacen posible este truco de magia computacional.

1. El punto de partida: La capa lineal tradicional

En una red neuronal estándar (como un Transformer), una capa lineal toma un vector de entrada \(x\) y lo multiplica por una matriz de pesos preentrenados \(W_0\) para producir una salida \(h\) (oculta o hidden).

La operación matemática es: \[h = W_0 \cdot x\]

Donde: * \(x \in \mathbb{R}^k\) (un vector de entrada de dimensión \(k\)). * \(W_0 \in \mathbb{R}^{d \times k}\) (la matriz de pesos preentrenada de dimensiones \(d \times k\)). * \(h \in \mathbb{R}^d\) (el vector de salida de dimensión \(d\)).

Cuando hacemos un Full Fine-Tuning, el optimizador intenta calcular una matriz de cambio llamada \(\Delta W\) (Delta \(W\)), de modo que los nuevos pesos sean \(W = W_0 + \Delta W\). La nueva salida sería: \[h = (W_0 + \Delta W) \cdot x = W_0 \cdot x + \Delta W \cdot x\]

El problema es que \(\Delta W\) tiene exactamente las mismas dimensiones gigantescas que \(W_0\) (\(d \times k\)), lo que exige gigabytes de memoria para calcular sus gradientes durante el entrenamiento.

2. La solución de LoRA: Factorización de bajo rango

En lugar de crear y optimizar esa matriz densa \(\Delta W\) de tamaño \(d \times k\), LoRA la factoriza (la divide) en el producto de dos matrices mucho más delgadas, llamadas \(B\) y \(A\):

\[\Delta W = B \cdot A\]

Aquí es donde ocurre la magia de las dimensiones (Álgebra Lineal): * \(A\) es una matriz de tamaño \(r \times k\). * \(B\) es una matriz de tamaño \(d \times r\). * \(r\) es el rango (rank), un hiperparámetro que usted elige (suele ser un número muy pequeño como 4, 8, 16 o 32).

Al multiplicar una matriz de \(d \times r\) por una de \(r \times k\), el resultado es, por pura definición de producto de matrices, una matriz de \(d \times k\). Matemáticamente la salida final del pipeline se reescribe así:

\[h = W_0 \cdot x + B \cdot A \cdot x\]

Durante todo el entrenamiento, \(W_0\) se congela por completo (no recibe gradientes). Solo se entrenan los números contenidos en las matrices delgadas \(B\) y \(A\).

3. Demostración numérica del ahorro de parámetros

Para entender el impacto real, hagamos una multiplicación con dimensiones típicas de un modelo de lenguaje moderno (por ejemplo, Llama o Mistral), donde la dimensión interna de una capa de atención podría ser \(d = 4096\) y \(k = 4096\).

Ajuste fino tradicional (\(\Delta W\) completa):

\[\text{Parámetros a entrenar} = d \times k = 4096 \times 4096 = \mathbf{16,777,216}\]

Ajuste fino con LoRA (usando un rango \(r = 8\)):

  • Parámetros de la matriz \(A\) (\(r \times k\)): \(8 \times 4096 = 32,768\)
  • Parámetros de la matriz \(B\) (\(d \times r\)): \(4096 \times 8 = 32,768\)

\[\text{Parámetros a entrenar} = (r \times k) + (d \times r) = 32,768 + 32,768 = \mathbf{65,536}\]

Conclusión del cálculo: Al pasar de 16.7 millones de parámetros a solo 65 mil, hemos reducido el coste de almacenamiento y cálculo de esa capa en un 99.6%, manteniendo una capacidad de aprendizaje prácticamente idéntica.

4. El truco de la Inicialización Matemática

Para que LoRA funcione desde el primer step de entrenamiento sin romper el conocimiento previo del modelo, la inicialización de las matrices \(B\) y \(A\) no puede ser aleatoria. Debe cumplir una condición estricta: al inicio, \(\Delta W\) debe ser exactamente \(0\).

Hugging Face y PyTorch lo resuelven así: 1. La matriz \(A\) se inicializa usando una distribución gaussiana (valores aleatorios normales). 2. La matriz \(B\) se inicializa completamente con ceros.

Al comenzar el entrenamiento, cualquier multiplicación por la matriz de ceros da cero: \[\Delta W = B \cdot A = 0 \cdot A = 0\]

Esto garantiza que en la primera iteración, \(h = W_0 \cdot x + 0 \cdot x\), por lo que el modelo se comporta exactamente igual que el modelo base original antes de empezar a ajustarse con sus datos.

5. Escalado mediante \(\alpha\) (Alpha)

Finalmente, LoRA aplica un factor de escala constante a la actualización para estabilizar el entrenamiento cuando cambia el rango \(r\). La ecuación final implementada en el código es:

\[h = W_0 \cdot x + \frac{\alpha}{r} (B \cdot A \cdot x)\]

Donde \(\alpha\) (alpha) es una constante. Al dividir \(\alpha\) entre \(r\), se asegura que cuando decida experimentar cambiando el rango (por ejemplo, subir de \(r=8\) a \(r=16\)), no necesite reajustar desde cero la tasa de aprendizaje (learning rate), ya que la escala de los gradientes se compensa dinámicamente.

Plantillas de instrucciones

Antes de comenzar el proceso de ajuste fino (fine-tuning), exploremos cómo los LLM entienden las instrucciones o prompts.

Usted ya está familiarizado con la forma en que los LLM responden a las instrucciones proporcionadas en texto plano, a menudo a través de prompting o indicaciones conversacionales. Aunque estos modelos están diseñados para comprender el lenguaje humano, no siempre están entrenados para interpretar las instrucciones y el historial de la conversación presentados exactamente en el mismo formato. La estructura específica de su prompt —la forma en que delimita la entrada del usuario, los mensajes del sistema o los turnos anteriores— puede variar de un modelo a otro.

Aquí es donde las plantillas de instrucciones (también llamadas plantillas de chat o chat templates) cobran importancia. Una plantilla de instrucciones es el formato de texto específico, incluyendo tókens especiales y reglas estructurales, con la que un LLM en particular fue entrenado para recibir instrucciones, contexto o un historial de chat. Utilizar la plantilla correcta para el modelo con el que está trabajando es crucial para garantizar que el modelo entienda adecuadamente su entrada y responda de la manera prevista.

Personalización del formato de la respuesta generada

Para guiar la generación del modelo de manera más precisa e influir en el inicio de su respuesta, una técnica común al utilizar plantillas de instrucciones consiste en añadir el marcador para el rol de asistente justo al final del prompt formateado. Esto le indica explícitamente al modelo que ahora es el turno del asistente para generar texto, y que su respuesta debe comenzar inmediatamente después de este marcador.

También podemos utilizar esta técnica para incentivar que la salida del modelo comience con un prefijo o frase específica, personalizando eficazmente el inicio de su respuesta. Por ejemplo, al añadir el marcador del rol de asistente seguido inmediatamente por GA: (geography assistant / asistente de geografía), establec# Decodificación de la salida numérica a texto legible tokenizer.decode(output_text[0], skip_special_tokens=True)emos la expectativa de que la respuesta generada por el modelo debe comenzar con esta cadena de texto específica. Configuramos los hiperparámetros de LoRA para el entrenamiento.

  • r (El rango de LoRA): Como ya se ha mencionado, es el parámetro más crítico para controlar el tamaño de las pequeñas matrices de adaptación que se añaden a las capas del modelo y, por lo tanto, determina el número de parámetros entrenables. Un valor de r más bajo significa menos parámetros, pero potencialmente una menor capacidad para adaptaciones complejas. En este ejemplo, r=4, lo que indica matrices de adaptación bastante pequeñas.
  • lora_alpha: Un factor de escala que ajusta la magnitud de las actualizaciones aprendidas por las capas LoRA. A menudo se configura de forma proporcional a r (por ejemplo, igual a ro 2 × r) para controlar el nivel de influencia que las adaptaciones de LoRA tienen sobre el comportamiento del modelo original. El escalado real que se aplica es típicamente lora_alpha / r. Aquí, lora_alpha=32.
  • lora_dropout: Especifica la tasa de dropout que se aplicará a las capas del adaptador LoRA durante el entrenamiento. Con la técnica de dropout, una fracción de las conexiones se ignora aleatoriamente durante cada paso de entrenamiento. Esto ayuda a evitar que los pequeños adaptadores LoRA sufran de sobreajuste (overfitting) con los datos de entrenamiento. Aquí se establece una tasa de dropout de 0.05 (5 por ciento).
  • bias: Controla la forma en que se manejan los términos de sesgo (bias) en las capas objetivo durante el entrenamiento de LoRA. Configurar bias="none" significa que los parámetros de sesgo en las capas específicas por target_modules no se entrenarán; permanecerán congelados en sus valores preentrenados. Otras opciones podrían entrenar todos los términos de sesgo o solo algunos específicos.
  • task_type: Le indica a la librería peft el tipo de tarea derivada (downstream task) para la que estás realizando el ajuste fino. Esto ayuda a la librería a identificar correctamente las capas o aplicar consideraciones específicas de la tarea. CAUSAL_LM indica modelado de lenguaje causal (causal language modeling), que es la tarea estándar para la mayoría de los LLM de generación de texto (predecir el próximo tóken basándose en los tókens anteriores).
  • target_modules: Una lista de cadenas de texto (strings) que especifica los nombres exactos de las subcapas o módulos dentro del modelo base preentrenado donde se deben inyectar las matrices del adaptador LoRA. Los objetivos habituales en los modelos Transformer son las matrices de pesos en el mecanismo de atención (como la consulta q_proj, clave k_proj, valor v_proj y salida o_proj) y las capas feed-forward (gate_proj, up_proj, down_proj). Al dirigirse solo a módulos específicos e importantes, LoRA mantiene el número de parámetros entrenables notablemente más bajo que en un ajuste fino completo (full fine-tuning).
  • modules_to_save: Especifica componentes adicionales del modelo, como lm_head, cuyos pesos originales también se volverán entrenables y se guardarán junto con los adaptadores LoRA. Ajustar de forma fina la capa lm_head es crucial, ya que afecta directamente a las probabilidades de salida del modelo y se beneficia de una adaptación directa a tu tarea específica.

Entrenamiento

Para gestionar el entrenamiento, utilizaremos SFTTrainer de la librería trl (Transformer Reinforcement Learning) de Hugging Face. Este conjunto de herramientas especializado simplifica el proceso de post-entrenamiento al proporcionar herramientas de alto nivel para el ajuste fino supervisado (supervised fine-tuning) y otras técnicas de alineación diseñadas para enseñar al modelo las preferencias humanas.

SFTTrainer es especialmente útil cuando se trabaja con técnicas PEFT como LoRA, ya que optimiza la transición desde la configuración de los parámetros de entrenamiento hasta la inicialización del entrenador con su modelo y datasets específicos.

Haz clic para ver el código 
from trl import SFTTrainer, SFTConfig
  • output_dir: Especifica dónde se guardarán los puntos de control (checkpoints) del modelo entrenado, los registros (logs) y otras salidas.
  • report_to: Se establece en "none" para evitar que se informen o reporten las métricas de entrenamiento a plataformas externas.
  • overwrite_output_dir: Al configurarlo en True, se permite al Trainer eliminar y volver a crear el directorio de salida (output_dir) si este ya existe.
  • do_train: Confirma que se debe ejecutar el proceso de entrenamiento.
  • learning_rate: Establece la tasa de aprendizaje (learning rate) inicial para el optimizador del modelo.
  • num_train_epochs: Define el número de veces (épocas) que el Trainer iterará sobre el conjunto de datos de entrenamiento (dataset) completo.
  • bf16=True: Activa el formato bfloat16. Esto reduce a la mitad el consumo de memoria frente a float32 y es altamente recomendado para GPUs modernas (Arquitectura Ampere o superior).
  • fp16=False: Desactivado a favor de bf16.
  • gradient_checkpointing=True: Crítico para la VRAM. Sacrifica una pequeña cantidad de velocidad de cómputo para re-calcular activaciones durante el paso backward en lugar de almacenarlas, ahorrando una cantidad masiva de memoria.
  • gradient_accumulation_steps=8: Acumula los gradientes durante 8 pasos antes de realizar una actualización de pesos. Esto permite simular un tamaño de batch mayor sin aumentar el consumo de memoria.
  • per_device_train_batch_size=1: Mantiene el batch en un sólo ejemplo para ahorrar memoria.

Realizamos una carga del modelo en dos pasos. Dado que PEFT guarda los cambios de manera incremental (como una “capa” sobre el modelo original), primero cargamos el modelo base y posteriormente inyectamos los adaptadores aprendidos.

  • Carga del modelo base: Inicializamos el modelo original (model_id).

  • Integración de PeftModel: `PeftModel.from_pretrained combina el modelo base con los pesos de entrenamienot (incluyendo el lm_head personalizado). Es aquí donde se restauran todas las configuraciones específicas del fine-tuning almacenadas.

  • Tokenizador: Cargamos el tokenizador desde el directorio del modelo para asegurar que coincida exactamente con el vocabulario utilizado durante el entrenamiento.

AdvertenciaDiferencias al cargar un modelo: Modelo Completo vs. Adaptadores LoRA

Al intentar cargar un modelo entrenado mediante técnicas PEFT (LoRA) utilizando únicamente la función AutoModelForCausalLM.from_pretrained(model_path), se producirá un error o una inicialización incorrecta. La explicación técnica reside en la naturaleza del almacenamiento de estos modelos:

  1. Estructura del directorio (model_path): El directorio resultante tras el entrenamiento con LoRA no contiene el modelo completo. Únicamente almacena los archivos de configuración de los adaptadores (adapter_config.json) y los pesos de las matrices de entrenamiento (adapter_model.safetensors), junto con las capas explícitamente marcadas para guardarse (ej. lm_head). Los pesos del modelo base, que comprenden la mayor parte de la arquitectura (capas de atención, bloques transformadores, etc.), no están presentes.

  2. Comportamiento del cargador: La función AutoModelForCausalLM.from_pretrained espera encontrar los pesos completos del modelo (ej. model.safetensors). Al no localizar estos archivos, el proceso genera errores de “archivo no encontrado” o intenta inicializar una arquitectura vacía, lo cual resulta inoperativo.

  3. Advertencias de carga (MISSING / UNEXPECTED): Cuando se intenta forzar la carga, el sistema reporta parámetros inesperados (los adaptadores, que no tienen dónde encajarse) y parámetros faltantes (la estructura base del modelo), lo que confirma la incapacidad del cargador estándar para reconocer la arquitectura completa sin el modelo base como referencia.

Conclusión: Para que el modelo sea funcional, es indispensable realizar la carga en dos pasos: * Primero, se inicializa el modelo base (AutoModelForCausalLM). * Segundo, se inyectan los adaptadores mediante PeftModel.from_pretrained, permitiendo que el sistema ensamble correctamente la arquitectura final.

def evaluate(model, tokenizer, data):
    # Tokenización y mapeo explícito de todo el diccionario al dispositivo acelerador
    tokenized_input = tokenizer(data, return_tensors="pt").to(device)
    
    # Generación segura pasando los tensores estructurados completos
    response = model.generate(
        **tokenized_input,
        max_new_tokens=10,
    )
    
    # Decodificación y segmentación guiada por el prefijo de respuesta
    decoded_message = tokenizer.batch_decode(response, skip_special_tokens=True)[0]
    decoded_category = decoded_message.split("Category: ")[1].strip()
    return decoded_category
